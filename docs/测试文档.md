## 一、测试策略

### 1.1 分层原则

按"逻辑价值 ÷ 测试成本"分配投入，不自下而上平均用力：

| 层级 | 覆盖对象 | 数量 | 执行方式 | 成本 |
|---|---|---|---|---|
| **L1 纯逻辑单元测试** | 静态计算函数、映射表、算法 | 118 个用例 | `Cmd+U` / CI | 极低 |
| **L2 数据层测试** | `CycleService` 写路径（内存态 SwiftData） | 32 个用例 | `Cmd+U` | 低 |
| **L3 集成 / UI 测试** | HealthKit、DeepSeek、界面交互 | 未自动化 | 手工 | 高 |

**为什么这样切**：L1/L2 覆盖的是"用户数据算得对不对、存得对不对"，这是本 App 的核心价值，也是最容易在重构中被静默改坏的部分；L3 依赖系统权限与网络，自动化投入产出比低，改为手工清单（见第五章）。

### 1.2 三类断言各自的作用

1. **数值断言** —— 锁死公式结果（如 BMR = 1320.25）。
2. **性质断言** —— 遍历整个参数域验证不变量，比逐点断言更能发现退化。
   例：`testPhaseOrderIsMonotonicWithinACycle` 遍历 15 × 9 组参数 × 每周期全部天数，
   验证阶段顺序永不回退。这类断言在重构后依然成立，不会因实现微调而误报。
3. **特征化断言（Characterization）** —— 把**已知缺陷**固化成断言，命名与注释中明确标注。
   目的是：缺陷被修复时测试会失败，强制开发者回来更新文档，而不是让缺陷悄悄消失。
   当前有 3 条，见第六章。

### 1.3 不以覆盖率数字为目标

一个函数有 100% 行覆盖率但只测了正常路径，价值远低于对同一函数做参数域扫描。
本项目优先覆盖**边界与非法输入**，因为历史上出的问题全在这儿（短周期崩溃、越界范围、负数时长）。

## 二、运行方式

### 2.1 命令行

```bash
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer

# 全部测试
xcodebuild test \
  -project WomenMoon.xcodeproj \
  -scheme WomenMoon \
  -destination 'platform=iOS Simulator,name=iPhone 17,OS=26.5' \
  -only-testing:WomenMoonTests

# 只跑某一层
xcodebuild test ... -only-testing:WomenMoonTests/CycleServiceTests
xcodebuild test ... -only-testing:WomenMoonTests/SeasonalTermsTests

# 单个用例
xcodebuild test ... -only-testing:WomenMoonTests/CycleCalculatorTests/testShortCycleDoesNotCrash
```

### 2.2 Xcode

打开 `WomenMoon.xcodeproj`，`Cmd+U`。
`project.yml` 已开启 `gatherCoverageData: true`，可在 Report Navigator 查看覆盖率。

### 2.3 前置条件

- `xcode-select` 需指向 `/Applications/Xcode.app/Contents/Developer`
  （本机原指向 Command Line Tools，会导致 `xcodebuild` 找不到 SDK）。
- **新增或删除源文件后必须执行 `~/.local/bin/xcodegen generate`**，否则文件不会进入 target。
- 测试目标已配置 `TEST_HOST`，因此 `FoodCategoryTests` 能通过 `Bundle.main` 读到
  `Resources/FoodDatabase.json`；若读不到会自动 skip 而非误报失败。

## 三、本环境的验证限制（重要）

本次测试代码的编写环境存在一项**硬性限制，必须在 Xcode 中复验**：

> 执行沙箱会阻止 `swift-plugin-server` 启动，导致 **SwiftData 的 `@Model` / `@Query` 宏无法展开**。
> 因此整个 App 的编译与测试**无法在本环境运行** —— 这是环境限制，不是项目问题。

### 3.1 已采用的替代验证手段

| 手段 | 覆盖范围 | 结果 |
|---|---|---|
| `swiftc -parse` 全量语法校验 | 全部 36+8 个源文件 | **0 错误** |
| 独立编译执行真实源码 | 周期判定、营养计算、节气算法、季节映射、`Date` 扩展口径 | **139 项断言全通过** |

独立验证的做法：把不依赖 SwiftData/SwiftUI 的真实源文件
（`Constants.swift`、`CycleCalculator.swift`、`NutritionCalculator.swift`、
`DateExtensions.swift`、`SeasonalTerms.swift`、`SeasonalWellnessService.swift`）
用 macOS SDK 单独编译成可执行文件，用最小替身补齐 `CycleRecord` / `FoodEntry` / `KeychainHelper`
三个编译期依赖，然后逐条执行测试文件中的期望值。

**这一步实际拦下了 2 个错误**：

1. `testSeasonalFoodsHasEnoughItemsForHomeCard` 断言"每个节气食材 ≥ 6 项"——
   实测只有 4–5 项，断言写错了。
2. `testSupplementFlagsAreDistinctAcrossPhases` 断言"四阶段补剂组合互不相同"——
   实测排卵期与卵泡期完全相同，只有 3 种组合。

### 3.2 仍需在 Xcode 中确认的

- **L2 全部 32 个用例**（`CycleServiceTests`）依赖 SwiftData，本环境无法执行。
  逻辑已按源码逐行核对，但内存容器的行为、`@MainActor` 隔离、`FetchDescriptor` 语义需要在真机/模拟器上跑一次。
- 由于无法编译，**不排除存在类型推断或访问控制层面的编译错误**。

**请在 Xcode 中执行一次 `Cmd+B` 与 `Cmd+U` 并回报结果。**

## 五、覆盖盲区与手工验证清单

### 5.1 无法自动化的部分及原因

| 范围 | 原因 | 建议 |
|---|---|---|
| HealthKit 全部读写（14 读 / 3 写） | `HealthKitService.shared` 是硬编码单例，**无协议抽象、无注入点** | 需先抽 `HealthKitProviding` 协议 + fake，才能覆盖"授权失败/无数据/部分类型缺失"三分支 |
| DeepSeek API 三个调用点 | 依赖网络与 Key | 用 `URLProtocol` mock 做契约测试，重点验证非 2xx 时**真实错误被吞**的问题 |
| 全部 SwiftUI 交互 | 需 XCUITest | 优先覆盖"点击无反应的 8 处空实现"与"从饮食页进补剂无法添加" |
| 通知、CloudKit | 未实现 / 未接通 | 仅需 smoke test 保证访问不崩溃 |
| Keychain | 需设备环境 | 手工验证 API Key 存取 |

## 六、已知缺陷在测试中的固化

以下 3 条用例**故意断言当前的缺陷行为**，命名与注释均已标注。
修复缺陷后这些用例会失败，**这是预期行为** —— 请连同本文件一起更新。

| 用例 | 固化的行为 | 风险 |
|---|---|---|
| `testAveragePeriodLengthIsCorruptedByReversedDateRange` | 结束日早于开始日时，平均经期为负数 | 用户看到"平均经期 -2 天" |
| `testAgeIsNegativeWhenBirthDateIsInTheFuture` | 出生日期可选未来日期，年龄为负 | 负年龄会被喂进 AI 上下文与 BMR 计算 |
| `testBMRDoesNotClampDegenerateInput` | `bmr` 不做入参钳位 | 绕过 UI 时可能算出负热量目标 |

此外，`testRecordingAnEarlierCycleMovesProfileStartDateBackward` 固化的是一条**值得商榷的口径**
而非明确缺陷 —— 补录更早的历史经期会让档案起始日倒退，进而影响首页"周期第 N 天"。
需要产品确认是否有意为之。

## 七、本次修复的缺陷（由测试驱动）

编写测试的过程中发现并修复了 1 个崩溃缺陷：

**`CycleCalculator.generatePredictions(months:)` 传入 ≤ 0 时崩溃**

```
for i in 1...months    // months = 0 → ClosedRange(1...0) → "Range requires lowerBound <= upperBound"
```

- 触发条件：任何调用方传入 0 或负数。当前调用方都传 6，属于**潜伏缺陷**。
- 影响：库函数不应要求调用方保证入参合法性；且此类崩溃会掀翻整个测试进程。
- 修复：`guard months > 0 else { return [] }`（`Services/CycleCalculator.swift`）。
- 回归用例：`testGeneratePredictionsWithNonPositiveMonthsReturnsEmpty`。

## 八、维护约定

1. **新增纯计算逻辑必须同时补 L1 测试**；涉及 `ModelContext` 读写的补 L2 测试。
2. **修改任何公式或阈值，必须同步更新对应断言**，并在提交信息中写明变更原因。
3. **发现缺陷但暂不修复时，写特征化用例固化**，并在第六章登记。
4. **参数域类断言优先**：能写成"对全部合法输入都成立"的，不要写成单点断言。
5. **同一业务口径只应有一处真源**（见 `CLAUDE.md`）。
   当前仍有未收敛的口径：`CycleTrackerView` 内两份手写的阶段判定副本、
   压力分档的 4 套阈值、经量档位的 3 套定义 —— 这些**只能在跨组件等价性测试中暴露**，
   补测试时优先为每一组口径加一条同型断言（参考 `testDateExtensionMatchesCalculator`）。
6. 运行 `Cmd+U` 前先确认 `xcodegen generate` 已执行过。
